# UCC-CES Management System — Technical Handover

**Document date:** 25 October 2026  
**Application release represented:** 1.1.7 (`0ebe81d`)  
**Project:** University of Caloocan City — Community Extension Services (UCC-CES)  
**Purpose:** Technical and operational handover of the implemented application, workflows, routes, authorization model, and database updates.

## 1. Executive summary

The UCC-CES Management System is a PHP 8.2 / MySQL application with a vanilla JavaScript single-page portal, a custom JSON API, and a separate public-facing CES landing page. It supports the community-project lifecycle from partner registration and proposal preparation through CES review and activation, event delivery, volunteer participation, attendance, evaluation, documentation, and reporting.

The changes captured in this handover consolidate the work recorded in the earlier development handovers and the current codebase, including:

- A public CES landing page and contact workflow, separated from the authenticated portal.
- Role-aware portal routes, navigation, dashboards, and server-side API authorization.
- Partner and volunteer registration with verification information and admin approval.
- Structured Project Brief proposals, partner collaboration, proposal review/activation, and project dossiers.
- Multi-date event scheduling, volunteer applications, attendance QR workflows, event evaluations, certificates, and completion archives.
- Partner and volunteer documentations, admin activity logs, notification workflows, reporting/export, and account/profile management.
- Additive SQL migrations that bring an existing database to the current schema.

This document describes what is present in the repository. It does not certify that every migration has been applied to a particular deployment database or that all production integrations have been exercised.

### Request flow

1. The project-root `.htaccess` serves `ces_landingpage/` at `/`, serves the portal shell for `/login` and `/portal`, and rewrites other portal paths into `public/`.
2. `public/.htaccess` routes `/api` and `/api/...` requests to `public/api.php`; unknown non-file paths resolve to the portal shell so a module URL can be opened or refreshed directly.
3. The browser application resolves the URL, restores the current page, checks the session using `GET /api/session`, and renders the role-appropriate workspace.
4. The API controller validates the session, requires a CSRF token on non-GET methods, applies module-level role checks, and then performs route-specific access and record-scoping checks.

The frontend derives its base path from the loaded `app.js` URL, so module/API links are built relative to the project deployment path. The HTML currently references `/UCC-CES/...` asset paths; update those references if the application is deployed under a different web-root path.

## 4. Roles, account lifecycle, and access controls

### Supported roles

The `users.role` enum contains exactly `admin`, `partner`, and `volunteer`. Student volunteers are represented by `volunteer_profiles.volunteer_type = 'student'`; “student” is not an independent login role. There is no separate Staff role in the current schema.

### Account state and authentication

- New Partner and Volunteer registrations enter `pending` status and require CES Admin review before sign-in.
- Accounts may be `pending`, `approved`, `rejected`, or `disabled`.
- Sign-in is limited to approved accounts. Rejection explanations are stored in `users.rejection_reason`.
- Admin-seeded temporary credentials can require a password change. Until the password is changed, the API restricts access to session inspection, password change, and logout.
- Passwords are stored as hashes; authentication uses session state and rotates session identifiers at authentication boundaries.
- Non-GET API requests require the session CSRF token in `X-CSRF-Token`.

### Role capabilities

| Capability | Admin | Partner | Volunteer |
|---|:---:|:---:|:---:|
| Overview/dashboard | Global administrative view | Own/linked project and event view | Personal participation view |
| Proposal register, dossier, review | Review all proposals; approve/reject/request revision and activate approved projects | Create/manage own drafts; submit proposals; participate in linked collaborations | — |
| Proposal collaboration | Invite/create collaborator accounts and manage proposals administratively | Invite/respond to collaborations; partner-created accounts remain pending review | — |
| Events and schedules | Global event management and recovery view | Own/linked event management and attendance operations | Browse available events and open event applications |
| Applications | Review applications within authorized event scope | Review applications for owned/linked events | Apply and review personal application status |
| Attendance | Administrative attendance/override operations | Attendance management for authorized linked events | Check in/out with event QR; view own records |
| Certificates | Issue/view authorized event certificates | Issue/view for authorized events | View/download own issued certificates |
| Reports and evaluation analytics | System-wide | Scoped to partner-owned or accepted-linked records | Personal submitted evaluations and participation views |
| Documentation | Administrative event/project context | Upload/view partner event records for linked completed events | Upload, view, and delete own volunteer documentation |
| Accounts and activity logs | Yes | — | — |
| Profile and event history | Own profile; authorized history | Own profile; authorized history | Own profile; personal history |
| Notifications | Yes | Yes | Hidden/not available in current notification module |

### Record-level rules

- Partner proposal access is scoped to the owner and accepted proposal-partner relationships.
- Partner event access is scoped to the organizer and event-partner links; related schedules, rosters, attendance, certificates, exports, and event reports follow the event access scope.
- Proposal and event documents/proofs are delivered through authenticated API endpoints; the uploads directory is not intended for direct public browsing.
- Volunteers must have an approved account to participate. An approved portal account does not itself approve an event application: volunteer enrollment and event application approval are separate states.
- UI role checks improve navigation and feedback, but API role checks, ownership checks, linked-partner checks, and event/volunteer status checks enforce access.

## 5. Implemented business workflows

### 5.1 Public CES landing and contact

The public site presents CES information, vision/mission and goals, featured programs/events, volunteer and partner information, and a contact section. “Sign In” / “Open Portal” links lead to the portal. Contact form submissions are handled by `ces_landingpage/contact_handler.php`; configure and validate its mail/hosting requirements separately from portal SMTP settings.

### 5.2 Partner and volunteer registration

Registration is a two-step wizard:

1. Collect account identity, contact details, password, and account type.
2. Collect role-specific verification information and upload proof:
   - Partner: organization/entity, category, official designation, verification file, and organization details.
   - Volunteer: classification/type and affiliation/student or other identifying information, plus proof where required.

Input is retained between steps and required fields are validated before submission. Newly submitted accounts remain pending until CES Admin review.

### 5.3 Account review and administration

Admin account management supports filtering/searching/sorting by status and account/affiliation attributes, viewing submitted details and proof, and reviewing an account. Approval, rejection (with a required reason), and disabling/status actions are submitted without a full-page reload. Account review is server-authorized for Admin only.

### 5.4 Project Brief, proposal review, and activation

Partner proposals are created and edited as structured Project Briefs. The wizard captures general project data, co-proponents, dates and venue, dynamic activity components, itemized estimated costs, justification, beneficiaries, outputs, risks/mitigations, external partnerships, classifications, and categories. The server validates the submitted structure and computes budget totals; client-side totals are not authoritative.

Proposal attachments are uploaded through a proposal-bound modal with document type and optional description/remarks. Supported file types and the 10 MB maximum are enforced server-side. Submission requires the signed proposal letter and Project Brief; MOA/MOU is optional.

The proposal lifecycle represented in the schema is `draft → submitted → under_review → revision/approved/rejected`, with an approved proposal eligible for `active`. CES Admin activation includes an explicit permanent-action confirmation and summary, creates/synchronizes the linked event and schedule transactionally, carries accepted partner links to event collaboration records, and notifies administrators. Project Brief PDFs and dossier data are access-controlled.

Partners can invite other approved partners to collaborate and respond to invitations. Admin-created collaborator accounts can be approved and invited within the admin flow; Partner-created accounts remain pending Admin approval. Pending accounts are not offered as approved collaborator choices.

### 5.5 Events, volunteer applications, and attendance

Events are linked to proposals and can contain multiple scheduled dates and activities. Admins have a global event dashboard, including a recovery view for approved/active proposals missing a linked event; partners see only their own or linked events.

Volunteers browse active opportunities, apply to events, and see application states (`pending`, `approved`, `rejected`, `withdrawn`). Event organizers review applications. The system supports date-specific attendance QR codes and check-in/check-out, verification state, manual organizer/admin attendance actions, participant counts, and attendance CSV exports. QR attendance is date-locked and uses an application secret key; the evaluation QR is exposed for the final event date. A daily absence-marking job is provided for past event dates.

Certificate issuance/download and volunteer event feedback are linked to event participation. A volunteer may submit one post-event evaluation per event (enforced by a unique event/volunteer key).

### 5.6 Documentations and event history

- Volunteers manage their own photo, report, accomplishment, or other documentation. They can upload, download, and delete their own records.
- Partners can add documentation for events they are authorized to access after the server-enforced completion delay (three full days).
- Completed events are available in Event History & Documentations rather than being mixed into active event management.
- Documentation metadata includes the stored relative path, original filename, MIME type, size, description, uploader/owner, and creation time.

### 5.7 Reports, evaluations, audit trail, and notifications

The reports module supports date-bounded, role-scoped reporting for projects/proposals, partner involvement, events, applications, attendance/volunteer hours, participant counts, evaluations, certificates, and documentations. Available filters include date range and relevant partner/category/status/search criteria; report data can be exported as CSV/PDF. Financial data is not included in the module-report set described in the earlier handover.

Evaluation analytics are available to Admin and scoped Partners; Volunteers see their own submitted evaluation history. Admin activity logs capture actor/role, action, entity, optional JSON details, IP address, and timestamp.

In-app notifications support listing, mark-one-read, and mark-all-read. Optional SMTP delivers email notifications. Password-recovery email is a required delivery path and returns an explicit configuration/delivery error if SMTP is unavailable.

### 5.8 Profile and password recovery

The profile page supports self-service account/profile details and security actions. Password recovery uses expiring one-time codes and reset tokens, request/attempt throttles, and a persistent reset record. On successful reset, session/CSRF state is refreshed. Temporary admin passwords require a password change before other portal work.

## 8. Deployment configuration and operations

### Required/optional configuration

Configuration is loaded from environment variables, with an optional ignored `config/local.php` override. Do not commit credentials or a real application key.

- Database: `CES_DB_HOST`, `CES_DB_PORT`, `CES_DB_NAME`, `CES_DB_USER`, `CES_DB_PASSWORD`.
- Application: `CES_APP_KEY` (unique random secret, at least 32 characters; required for date-locked attendance QR tokens), `CES_APP_URL` (recommended for QR links opened on other devices).
- SMTP: `CES_SMTP_HOST`, `CES_SMTP_PORT`, `CES_SMTP_USERNAME`, `CES_SMTP_PASSWORD`, `CES_SMTP_ENCRYPTION`, `CES_SMTP_FROM`, optional `CES_SMTP_FROM_NAME`.
- PHP requirements noted in setup: PDO MySQL and Fileinfo; Composer dependencies installed from `composer.lock`.
- Uploads are stored under `public/uploads/`, with direct Apache access denied and API-based file delivery. The configured upload maximum is 10 MB.

For Gmail recovery delivery, the README recommends Gmail SMTP (`smtp.gmail.com`, port `587`, `tls`) with an app password, not a normal account password. Portal SMTP notifications may be disabled, but password recovery requires working SMTP and returns an explicit error if it cannot send.

### Local setup and maintenance commands

See [`README.md`](../README.md) for the full XAMPP setup. Key operations:

```powershell
C:\xampp\php\php.exe C:\xampp\htdocs\UCC-CES\scripts\create-admin.php
C:\xampp\php\php.exe C:\xampp\htdocs\UCC-CES\scripts\seed-admin.php
C:\xampp\php\php.exe C:\xampp\htdocs\UCC-CES\scripts\seed-sample-data.php --apply
C:\xampp\php\php.exe C:\xampp\htdocs\UCC-CES\scripts\mark-absences.php
C:\xampp\php\php.exe -S 127.0.0.1:8027 -t C:\xampp\htdocs\UCC-CES\public C:\xampp\htdocs\UCC-CES\scripts\dev-router.php
```

- Use either first-admin approach as appropriate; the seeded admin script prints a one-time temporary password which must be changed.
- The sample seeder is for local development only. It replaces project/event and other non-account data, requires seeded prerequisites and demonstration PDFs, and must not be run against production.
- Schedule `mark-absences.php` daily after midnight Manila time as an operational job; validate the production scheduler and timezone.
- Apache must allow the project rewrite rules (`mod_rewrite` and appropriate overrides). Verify upload size limits and writable upload directories in PHP/Apache configuration.

## 9. Verification and known limitations

Prior handover notes record PHP syntax checks, JavaScript parsing, `git diff --check`, browser UI checks using mocked API responses, direct-route/SPA fallback checks, and selected proposal wizard, upload-modal, report, and event-form smoke tests. Earlier checks did not constitute full authenticated production integration testing. In particular:

- Report SQL and CSV/PDF paths should be checked against representative data in the intended database.
- Validate each role's API access with real authenticated accounts, including denied access to unrelated partner/event/document records.
- Exercise uploads using real supported files and invalid/oversized/type-mismatch cases.
- Verify password recovery through the configured SMTP provider, attendance QR scanning from a separate device, and the daily absence job.
- Confirm migration state and backup/restore procedures for the target environment.
- Confirm deployment base-path assets and Apache rewrite/protected-upload behavior when not hosted at the repository's documented `/UCC-CES` path.
- Check the landing contact handler's mail delivery and anti-abuse behavior for the target deployment separately.

Do not infer migration completion or production readiness from source code presence alone. For any production release, back up the database and uploads, apply only pending migrations, verify configuration/secrets, and execute authenticated end-to-end checks.
