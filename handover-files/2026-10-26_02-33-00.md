## 1. Executive summary

UCC-CES is a PHP 8.2 / MySQL application running under Apache/XAMPP. It has a public CES landing page, an authenticated vanilla-JavaScript portal, and a custom PHP JSON API backed by PDO and MariaDB.

The latest implementation hardens date-specific QR attendance. An approved volunteer scans the same date QR twice in the valid sequence:

1. First successful scan records **Time In**.
2. A second scan within 60 seconds is rejected as a likely accidental duplicate.
3. The next valid scan records **Time Out**.
4. Further scans are rejected because attendance is complete.

The server determines identity, event date, transition and timestamps. Signed QR tokens are checked against the database and `CES_APP_KEY`; event/application approval, date eligibility, and state transitions are checked on the backend. The database enforces one attendance row per application/event date, blocks Time Out before Time In, stores attendance record timestamps, and stores successful scan request IDs to detect exact request replays.

The integrity migration has been applied to the local XAMPP database and the API sequence was exercised over HTTP using a temporary approved volunteer and today’s active event. Test data and hash changes were cleaned up. Do not interpret that local integration test as production acceptance testing.

## 4. QR attendance workflow

### 4.1 QR generation

The event date QR is served by `GET /api/event-dates/{eventDateId}/qr`, implemented by `showEventQr()`:

- Requires an authenticated event organizer/admin according to the existing event authorization helper.
- Requires an approved/active proposal and that the event date is the current date in the configured application timezone.
- Computes an HMAC-SHA256 token from the database event ID, database event-date ID, and scheduled date, using the configured `CES_APP_KEY`.
- Verifies/refreshes the stored SHA-256 token hash for that event date.
- Returns a JSON QR payload containing the date ID and signed token, plus a rendered QR image.

The QR payload does not trust a browser-supplied event ID as its authority. Event identity and date are looked up from the referenced database event-date row and are cryptographically bound into the HMAC. An edited token, changed date ID, invalid signature, or stored hash mismatch is rejected.

### 4.2 Attendance scan validation and transition

`scanAttendance()` performs the following checks before committing attendance:

1. Requires a logged-in session and the volunteer role.
2. Parses a valid event-date ID, 64-character lowercase hexadecimal signed token, and 32-character lowercase hexadecimal scan-request ID.
3. Loads event ID, date, QR hash, and proposal state from the database.
4. Verifies the HMAC and compares the QR token’s SHA-256 hash with the stored date token hash.
5. If the request includes UI event/date context, validates that context against the database QR identity.
6. Requires the proposal to be approved or active and the database event date to equal the application’s current date. Past and future dates are rejected.
7. Begins a database transaction and rejects an already-used scan-request ID.
8. Locks the volunteer account and confirms its database role/status is still approved.
9. Locks the volunteer’s event application and confirms it remains approved for that event.
10. Locks and reads the one attendance row for the application and event date.
11. Applies the state rules:
    - No row: insert one Present row with server-generated `CURRENT_TIMESTAMP` as Time In.
    - Existing row without Time In: fill Time In, preserving one row.
    - Time In without Time Out: reject before 60 seconds; afterwards set Time Out with `CURRENT_TIMESTAMP`.
    - Time In and Time Out: reject as completed.
12. Inserts the successful scan-request ID in the same transaction, reads the persisted timestamp, and commits.
13. Writes an Activity Log entry after successful commit and returns the saved server timestamp.

Rejected validations produce an `attendance.scan_rejected` Activity Log with a reason code, actor from the session, event-date ID if known, event ID if known, role and IP as provided by the existing logger. QR secrets and raw token values are not included in audit details.

### 4.3 Concurrency and duplicate protection

- `event_applications` has a unique event/volunteer key. Locking the approved application serializes scans for the same volunteer/event.
- `attendance` has unique key `uq_attendance_application_date (application_id, event_date_id)`. Combined with the unique application and unique event-date constraints, this permits one attendance row per volunteer/event/date.
- The attendance row is read `FOR UPDATE`; Time Out also uses a conditional update requiring a non-null Time In and null Time Out.
- `attendance_scan_requests.scan_request_id` is a primary key. Replaying the same request ID cannot be recorded twice.
- A client uses a new cryptographically random request ID per submission. Repeated submissions with new IDs still cannot repeat a completed transition; a rapid second scan is blocked by the one-minute grace interval.
- No user-provided timestamp, volunteer ID, attendance status, or transition action is used to decide what to write.

### 4.4 Scan result messages

Successful responses include `action`, `message`, and database-returned `recordedAt`:

- `check_in`: “Time In recorded successfully.”
- `check_out`: “Time Out recorded successfully. Attendance completed.”

The volunteer scanner formats and displays the server timestamp. Rejections return a short, direct reason such as invalid attendance QR, wrong event/date context, unavailable date, unapproved application, Time In already recorded, or completed attendance. Unexpected PDO/internal errors are handled by the API’s existing generic error response and server-side error log.

## 5. Data model and database integrity

### Existing constraints retained

- `event_dates`: primary key on date row; unique `(event_id, event_date)`.
- `event_applications`: unique `(event_id, volunteer_user_id)`.
- `attendance`: unique `(application_id, event_date_id)`.
- These constraints represent one attendance record per volunteer/event/date without duplicating event or volunteer IDs into `attendance`.

### Added by this task

`attendance`:

- `created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`
- `updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`
- `chk_attendance_time_order`: if Time Out is set, Time In must exist and Time Out must be greater than or equal to Time In.

`attendance_scan_requests`:

- `scan_request_id CHAR(32)` primary key, ASCII binary comparison.
- `attendance_id` foreign key to the attendance row, cascade-deleted with that row.
- `action` enum for `check_in` or `check_out`.
- `created_at` timestamp.

The request table contains identifiers for successful API scan requests only. Rejections are recorded in Activity Logs rather than in this table.

## 6. Application key and environment configuration

`config/app.php` reads `CES_APP_KEY` from the process environment and then overlays the ignored `config/local.php` using `array_replace_recursive`. In the local XAMPP instance, Apache did not have `CES_APP_KEY` in its process environment and `config/local.php` did not exist. An ignored local override was created with a cryptographically generated 256-bit random key. The key value is intentionally not included in this handover or Git.

Important:

- Preserve the local `config/local.php`; it is ignored by Git and must not be committed or copied into public documentation.
- A new environment needs its own randomly generated key of at least 32 characters. A 64-character hex string from 32 random bytes is suitable.
- Use the same key across application instances that must validate the same current QR tokens.
- Rotating the key invalidates previously generated QR signatures. The normal QR generation endpoint can refresh the stored token hash when an authorized organizer regenerates today’s QR.
- Keep `CES_APP_KEY` private and out of logs, responses, screenshots, and repository history.
- Evaluation QR generation uses the QR renderer and URL, not this attendance HMAC. Set `CES_APP_URL` for QR links that must resolve from other devices; otherwise the API derives the URL from the request host.

The README documents generation and local configuration. The actual secret must be obtained from the local XAMPP configuration, not this file.

## 10. Remaining risks and operational notes

1. **The one-minute grace interval is deliberate behavior.** It helps prevent accidental double scans; changing it is a product decision and should be tested against actual event operations.
2. **MariaDB enforces timestamp order, but not the entire business state machine.** The state sequence is enforced in the API transaction. The unique key and CHECK constraint protect the most important invariants if another application path is added.
3. **Other attendance write path:** `overrideAttendance()` remains an administrative manual status override and intentionally does not follow the volunteer QR state machine. It can create/modify a manual Present/Absent/Excused row. Review this route if the requirement is later expanded to prohibit administrators from overriding recorded Time In/Time Out.
4. **Fresh deployment:** install Composer dependencies, configure database and a unique key, apply the complete current schema, and configure Apache rewrite/overrides. Do not copy secrets from another deployment.
5. **Existing deployment:** back up the database and apply the new attendance migration once before deploying the API code that writes to `attendance_scan_requests`.
6. **Worktree:** the repository contains unrelated uncommitted changes from earlier tasks. Do not reset, clean, or revert them during deployment or follow-up work.
7. **No production deployment or commit is represented here.** The local XAMPP database was changed directly after a backup; replicate the migration through the target environment’s controlled database procedure.
